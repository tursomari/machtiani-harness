You MUST use forge for all file modifications. Forge is orders of magnitude more reliable than attempting to edit files directly. Forge has full read-write access to the filesystem and can execute complex file editing tasks described in high-level natural language, similar to tools like Claude Code, Codex CLI, or Aider. It can create new files, modify existing files, rename or delete files, and make targeted edits across multiple files in a single invocation.

When using forge, write a handoff note describing the desired change to a file using these principles:
- Use plain English paragraphs. No code fences, no backticks, no markdown formatting.
- Specify the exact file path to change.
- Describe concretely what to add, remove, or modify.
- Include the instruction "do not stage" unless staging is explicitly requested.
- For complex multi-file changes, describe each change clearly in sequence.

To invoke forge, pass the handoff note as a single-quoted string argument to mct-forge:
  mct-forge 'Your handoff note text here. Do not stage.'

The mct-forge command feeds the note to forge and returns forge's assistant reply as its output. You do not need to write any file to /tmp or anywhere else - mct-forge handles everything internally. After the command completes, verify the diff shows the correct changes and confirm nothing was staged unless you explicitly requested it.

IMPORTANT - common mistakes to avoid:
- Do NOT use command substitution: mct-forge $(...) is BLOCKED by the command validator
- Do NOT pipe to mct-forge: echo ... | mct-forge is WRONG
- Do NOT use xargs: ... | xargs mct-forge is WRONG
- Do NOT use backticks in the handoff note - they are BLOCKED by the command validator
- Avoid single quotes/apostrophes in the handoff note (like don't, can't) - they break the single-quoted string. Rephrase to avoid them.
- Always pass the note as a single argument: mct-forge 'your note'

The total command length (including "mct-forge " prefix) must not exceed 8192 bytes. If your note exceeds that limit, split the work across multiple forge invocations.

## Skyvern Web Interaction
- The shell-agent can interact with web pages using the Skyvern API server running locally on port 8000.
- To submit a navigation/extraction task: POST http://localhost:8000/api/v1/tasks with JSON body {"url": "<target>", "prompt": "<what to do>", "engine": "skyvern-1.0"}, including header x-api-key: <key from third_party/skyvern/.env>.
- To poll results: GET http://localhost:8000/api/v1/tasks/{task_id} with the same x-api-key header. Wait for status: "completed" or status: "failed" before acting on results.
- For launch: ensure the Skyvern server is running (python3 -m skyvern run server with LLM_KEY=DEEPSEEK_V4 and DeepSeek credentials).
- If a task fails with LLM_ERROR, verify LLM_KEY is set correctly.
- Scripts/longer workflows: point users to Skyvern docs in third_party/skyvern/docs/ for the SkyvernScript YAML format; the shell-agent can read those docs to construct scripts when needed.
- Captcha/authorization obstacles: if the task returns an error or screenshot showing a captcha/login wall, do not attempt to bypass it programmatically. Report the obstacle to the planner with the page URL so the user can manually clear it, and pause the task until instructed to retry.
- Interactions must be natural and non-abusive — single page loads, reasonable delays, no automated form submissions without explicit user approval.
- The skyvern Python package is installed in the local environment; the CLI python3 -m skyvern is available for diagnostics and helper commands.
